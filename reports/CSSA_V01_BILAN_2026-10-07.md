## 1. Résumé exécutif

Le projet est passé d'un simple domaine Administration théorique à un démonstrateur CSSA capable de simuler une saison complète d'organisation.

État actuel :

- socle universel / runtime portable : validé ;
- domaine Administration portable : validé ;
- premier modèle CSSA public : validé ;
- kit d'ingestion terrain : prêt ;
- scénarios réalistes isolés : validés ;
- audit saison complète : validé ;
- simulateur saison complète : validé ;
- données internes réelles CSSA : encore absentes ;
- actions externes réelles : toujours bloquées.

La conclusion principale est que le verrou technique n'est plus "peut-on brancher un club comme domaine ?". La question devient maintenant "est-ce que le système reste cohérent quand toute l'organisation vit en parallèle ?".

## 2. Ce qui est réellement prouvé

### Runtime universel

Le chemin suivant fonctionne :

```text
CSSA / Administration
 -> DomainStateRefV0
 -> GovernancePayloadV0
 -> resolver portable aggregate-only
 -> REAL DomainAggregate
 -> REAL GuardX108
 -> CanonicalDecisionEnvelope
 -> décision persistée/vérifiée
 -> replay
 -> execution gate
 -> provider borné READONLY
 -> receipt
```

KX108_ONLY reste l'autorité de décision.

Aucun resolver portable ne peut fournir directement une DecisionEnvelope : l'extension ne produit que le DomainAggregate, puis le vrai GuardX108 tranche.

### CSSA public

Le modèle public couvre notamment :

- 19 structures d'équipes ;
- R1, R2, U20 R1, formation, féminines et école de foot ;
- rôles administratifs/comptables/secrétariat ;
- matchday, sécurité, partenaires, communication ;
- règles LGEF 2026-2027 ;
- licences, FMI, changements de rencontre, correspondance officielle ;
- abonnements, billetterie, équipements, partenaires ;
- sources publiques contradictoires ou périmées.

## 3. Ce que les tests nous ont appris

### A. Le club ne peut pas être modélisé comme "une équipe + un secrétariat"

Le CSSA doit être traité comme une organisation multi-pôles :

- compétitions ;
- académie/licences ;
- transport ;
- finance/comptabilité ;
- partenaires ;
- supporters/billetterie ;
- matchday ;
- communication ;
- bénévoles/staff ;
- éducation ;
- preuve/audit.

### B. La cohérence des sources est déjà un problème réel

Les sources publiques peuvent être en retard ou se contredire.

Exemples détectés :
- organigramme Manager Général périmé après départ officiel ;
- étiquette publique de la réserve encore en R3 alors que la saison actuelle la place en R2 ;
- formulation "+12 matchs à domicile" vs abonnement couvrant 13 matchs de championnat ;
- site lui-même en phase de mise à jour.

Conséquence :
le système doit gérer la fraîcheur, la provenance et les contradictions avant de considérer une donnée comme vérité.

### C. La majorité des risques viennent des dépendances, pas des règles individuelles

Les cas les plus intéressants ne sont pas "une règle est fausse", mais :

- une décision LGEF tarde ;
- le mail supporter est déjà prêt ;
- le planning matchday dépend encore de l'ancien horaire ;
- un transport est en conflit avec un autre déplacement ;
- un partenaire attend une hospitalité ;
- une validation manque ;
- une source est périmée ;
- une personne-clé est absente.

C'est ce qui justifie la prochaine phase de stress organisationnel.

### D. Les chiffres publics sont exploitables seulement avec leurs limites

Ce qui peut être utilisé :
- tarifs licences ;
- tarifs LGEF ;
- prix abonnements ;
- nombre public de partenaires ;
- snapshots abonnés ;
- calendriers/groupes ;
- composition des équipes ;
- estimation de distances.

Ce qui ne doit pas être inventé :
- revenus partenaires ;
- mix exact des abonnements ;
- budget réel 2026-2027 ;
- salaires ;
- politique de frais ;
- relation opérationnelle exacte Association/SAS.

### E. Les données RH privées peuvent être utiles, mais elles ne doivent pas devenir le cœur du modèle

Une fiche de paie réelle peut aider à confirmer :
- entité employeuse ;
- type de contrat ;
- périodicité ;
- certaines indemnités/frais.

Mais le système n'a pas besoin du salaire exact pour valider l'architecture Administration.

Le plus utile est le workflow :
qui paie, qui valide, qui rembourse, qui planifie, quels outils sont utilisés, quels documents circulent.

## 4. Incidents / corrections trouvés pendant les tests

### F2.5
Un premier design autorisait trop de liberté au resolver portable.

Correction :
- extension -> DomainAggregate uniquement ;
- GuardX108 réel dans le runtime ;
- faux ALLOW forgé explicitement rejeté.

### F3E
Premier run :
- 194 PASS / 1 FAIL ;
- cause : dérive de 0,10 km due aux arrondis trajet par trajet.

Correction :
- conserver la précision jusqu'à l'agrégation saison.

Closure :
- 195 PASS / 195.

Ces deux incidents sont utiles : ils montrent que la forge/test découvre réellement des défauts et ne sert pas uniquement à confirmer ce qu'on avait déjà décidé.

## 5. Ce qui manque encore

### Réalité terrain CSSA

Toujours inconnu :

- qui fait réellement quoi ;
- quelles boîtes mail sont utilisées ;
- outils internes ;
- délégation/remplacement ;
- vraies validations ;
- vraies feuilles de frais ;
- transport réel ;
- budget réel ;
- contrats ;
- organisation Association/SAS ;
- exceptions locales ;
- habitudes non écrites.

### Concurrence organisationnelle

F3E génère la saison, mais ne teste pas encore suffisamment :

- deux équipes voulant le même véhicule ;
- absence d'un responsable ;
- budget consommé plus vite que prévu ;
- multiples urgences au même moment ;
- partenaire + match + FMI + déplacement en conflit ;
- priorisation des dossiers ;
- délégation en cas de vacance ;
- propagation d'un retard à plusieurs services.

C'est le rôle de F3F.
